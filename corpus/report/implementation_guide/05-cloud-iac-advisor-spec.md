# 05 — Cloud / IaC Advisor Output Spec

**Track B.** This is what the advisor *emits to the user* — not how the project is deployed. Resume priority #2. Input: the resolved `requirement_vector` + `decision_log` from the router. Output: two linked diagrams + a Terraform module sketch + a use-case-relative strengths/weaknesses panel.

## 5.1 Topology selection (`synth/topology.py`)

Fixed catalog (report §6), no free composition — the decision must be auditable:

1. single-stage dense · 2. single-stage hybrid · 3. two-stage dense+rerank · 4. two-stage hybrid+rerank · 5. adaptive/agentic

Selection = hard-constraint filtering first (e.g. A2 high removes dense-only; A12 gated removes direct-answer), then quality optimization within survivors using the requirement vector, then tie-break by the user's stated priority. Every selection step cites the requirement attribute and the corpus section that justifies it. The `decision_log` already carries the why; topology selection appends its rationale to it.

## 5.2 The two linked diagrams

**Pipeline diagram** — the selected topology's stages: parse/chunk → embed → hybrid retrieve → rerank → generate (stages present/absent per topology).

**Deployment diagram** — the *same stages projected onto infrastructure* via a fixed, auditable stage→infra map:

| Pipeline stage | Infra component | Cloud pillar |
|---|---|---|
| Embed | inference service (batchable) | Compute |
| Vector search | vector DB + ANN index (memory-bound) | Databases |
| BM25 | lexical index | Storage |
| Rerank | cross-encoder service (GPU, latency-dominant) | Compute / Scalability |
| Generate | LLM endpoint (pluggable) | Compute |
| (cross-cutting) | VPC/egress, IAM/KMS/RBAC, metrics/tracing, autoscale | Networking, Security, Monitoring, Scalability |

"Linked" = the two diagrams share node IDs; every deployment node carries the pipeline-stage ID it serves, so hovering/selecting a pipeline stage highlights its infra footprint. Baseline render: one figure, two subgraphs, dashed projection edges. Stretch: interactive SVG hover-linking.

All 7 cloud pillars (Compute, Networking, Storage, Databases, Security, Monitoring, Scalability) must appear in every deployment diagram — the cross-cutting row guarantees coverage even for minimal topologies.

## 5.3 Terraform emit (`synth/terraform_emit.py`)

Illustrative IaC (not applied — sidesteps the Spaces constraint, fully demonstrates the skill). Emitted tree: root + `variables.tf`/`outputs.tf` + `environments/{dev,staging,prod}.tfvars` + `modules/{compute,networking,storage,database,security,monitoring,scalability}/`, parameterized from the requirement vector.

The 7 IaC principles, each demonstrably present:

| Principle | Where |
|---|---|
| Declarative definitions | all HCL, no imperative scripts |
| Repeatable provisioning | same tfvars → same plan (mirrors ingestion idempotency) |
| Change previews | README documents `terraform plan` as the gate |
| Shared state | remote backend + lock block, commented |
| Reusable modules | the 7 modules, input-parameterized |
| Environment consistency | `environments/*.tfvars` over one module set |
| Auditable deployment history | plan/apply log retention guidance |

Emitted HCL must be genuinely valid — a fake-looking tree undercuts the entire #2 signal. Budget real build time here.

## 5.4 Strengths/weaknesses panel (`synth/panel.py`)

Generated by intersecting the chosen topology's report-backed profile with **each requirement the user actually stated** — never generic. Per stated requirement: what this design does well, what it does poorly, the corpus citation, the explicit tradeoff accepted. Pull weaknesses from the corpus's deliberately-collected failure-mode content and the domain cards' "canonical failure modes" — these do not fall out of how-to text and are what make the panel credible.
